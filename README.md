# <Название проекта>

> Это шаблон процесса и документации для разработки игры с помощью ИИ-агентов.
> Это НЕ запускаемая игра и не игровой код: каталоги `src/`, `tests/`, `content/`
> появятся позже, в реальном проекте, после выбора движка.

## Как начать новый проект

1. Скопируй шаблон в новую папку и создай Git-репозиторий.
2. Выбери движок, Git-хостинг и ИИ-инструменты — в шаблоне это слоты «TBD».
3. Заполни `docs/product/vision.md` и `docs/product/scope.md`, утверди у владельца.
4. Дополни `.gitignore` правилами выбранного движка и инструментов.
5. Веди системы в `docs/systems/INDEX.md`, задачи ставь по `docs/workflow/task-template.md`.
6. Приёмка шаблона: чистая сессия на трёх пробных задачах — чек-лист ниже.

Подробное руководство для владельца игры, простым языком и без чтения кода —
`docs/workflow/human-playbook.md`.

Если выбранный инструмент НЕ загружает `AGENTS.md` сам, для него нужен адаптер
или явная инструкция «прочитай AGENTS.md в начале задачи». Это проверяется
в чистой сессии (см. чек-лист): агент, не прочитавший правила, приёмку не проходит.

## Приёмка чистой сессией

Чистая сессия — запуск агента без истории прежних чатов. Это ПЛАНОВЫЕ dry-run
сценарии: шаблон — ещё не игра, кода и данных нет, поэтому агент ничего не
реализует и не изменяет файлы. Его задача — найти нужные документы, описать
план действий и перечислить проверки, которые он бы запустил.

Три пробных запроса:

1. «Добавь новый предмет» — опиши, куда бы ты внёс данные и что проверил бы.
2. «Измени правило механики, у которой есть зависимости» — например, порядок событий в бою; до любой правки назови затронутые системы.
3. «Предложи изменение общего правила для агентов» — ожидается: агент предлагает текст правки `AGENTS.md` и ждёт отдельного подтверждения; сам файл он НЕ меняет — это прямо запрещено правилом в `AGENTS.md`.

Чек-лист успешного прохождения (по всем трём задачам):

- Агент сам нашёл и прочитал: `AGENTS.md` → `docs/INDEX.md` → `docs/systems/INDEX.md`; перед отчётом открыл `docs/workflow/testing.md`.
- Если страницы нужной системы нет (в пустом шаблоне реестр пуст), агент честно отметил нехватку контекста и спросил владельца, а НЕ выдумал систему, страницу или данные.
- В задаче 2 агент назвал затронутые SYS-ID и зависимости в обе стороны по реестру — до описания правки; если реестр пуст, см. пункт выше.
- Границы dry-run соблюдены: файлы и игру агент не менял, тесты и сборку не запускал — достаточно прочитать документы и выдать план; проверки, которые он не запускал, отмечены как незапущенные.
- Агент не принял без одобрения: новые или неоднозначные игровые решения (баланс, поведение, видимые игроку эффекты), push/публикацию, подключение сервисов; в задаче 3 — `AGENTS.md` не тронут, предложена правка и ожидается подтверждение.

## Структура

| Путь | Назначение |
|---|---|
| `AGENTS.md` | Постоянные правила для ИИ-агента; точка входа в начале задачи |
| `CHANGELOG.md` | История выпущенных изменений (журнал, не спецификация) |
| `docs/INDEX.md` | Каталог всех документов |
| `docs/product/` | Замысел игры и текущий утверждённый объём |
| `docs/systems/` | Реестр систем и страницы механик |
| `docs/architecture/decisions/` | Записи архитектурных решений (ADR) |
| `docs/workflow/` | Процессы: задачи, проверки, ассеты, данные |

## Мини-словарь

- **Источник истины** — единственное место, где хранится данный вид информации; остальные ссылаются на него, а не копируют.
- **SYS-ID** — постоянный идентификатор системы (например, `SYS-COMBAT`); не меняется при переименовании.
- **ADR** — короткая запись об архитектурном решении со статусом («предложено / принято / заменено»).
- **Provenance** — происхождение ассета: источник, модель, prompt/seed, права, одобрение.
- **Smoke-тест** — быстрый запуск «включается и не падает».
- **TBD** — «будет определено позже» (зависит от будущего движка или Git-хостинга).
- **Чистая сессия** — запуск агента без истории прежних чатов; проверяет, что документации достаточно без устного контекста.
